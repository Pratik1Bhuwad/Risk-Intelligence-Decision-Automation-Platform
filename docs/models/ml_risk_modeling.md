## 3. Strict Chronological Temporal Split Strategy

To prevent look-ahead bias and cross-split contamination, splitting strictly uses the discrete simulation temporal index (`step`, 1 to 743 hours). Random k-fold cross-validation is **prohibited** as it allows future macro dynamics and evolving fraud rings to leak into past predictions.

$$\text{Train}(t \le 400) \quad \longrightarrow \quad \text{Validation}(400 < t \le 550) \quad \longrightarrow \quad \text{Test}(550 < t \le 743)$$

### Temporal Partition Dimensions:
| Split Fold | Step Range | Total Rows | Share | Fraud Count | Fraud Prevalence | Purpose |
| :--- | :---: | :---: | :---: | :---: | :---: | :--- |
| **Train** | Steps 1–400 | 5,787,030 | 90.95% | 4,477 | 0.07736% | Fitting model weights and preprocessors |
| **Validation** | Steps 401–550 | 378,989 | 5.96% | 1,588 | 0.41901% | Model selection, calibration, threshold tuning |
| **Test** | Steps 551–743 | 196,601 | 3.09% | 2,148 | 1.09257% | Final temporal test partition (qualified holdout — see disclosure note below) |
| **Total** | Steps 1–743 | 6,362,620 | 100.0% | 8,213 | 0.12908% | Entire PaySim Dataset |

*Note: All three splits contain thousands of fraud cases and reflect real temporal shifts in transaction volume.*

## 6. Probability Calibration & Decision Thresholds

### A. Probability Calibration
Post-hoc probability calibration was evaluated using **Platt Scaling (Sigmoid)** fit strictly on the validation fold (`y_val`, `val_probs`).

- **Validation Fold Brier Score**:
  - Raw Brier Score: `0.000003`
  - Calibrated Brier Score: `0.000003` (Improvement: `0.000000`)
- **Out-of-Time Test Set Brier Score**:
  - Raw Test Brier Score: `0.00001072` ($\approx 1.1 \times 10^{-5}$)
  - Calibrated Test Brier Score: `0.00001389` ($\approx 1.4 \times 10^{-5}$)

#### Calibration Behavior & Retention Decision:
On the test set, the calibrated Brier score exhibited a slight numerical increase ($+0.000003$). This occurs because Platt scaling maps raw overconfident probabilities near $1.0000$ down to a calibrated ceiling of $\approx 0.9816$. For the 2,146 true positive fraud transactions, $(1 - 0.9816)^2 \approx 0.00034$, slightly increasing squared loss compared to uncalibrated $1.0000$.

Calibration is intentionally retained in the production pipeline because:
1. **Analyst Interpretability**: It maps raw tree leaf margins to smooth empirical probability estimates, preventing false overconfidence in automated systems.
2. **Monotonicity & Invariance**: It strictly preserves probability rank ordering.
3. **Decision Stability**: It produces identical multi-tier decision boundaries and 0 false positives across 194,453 test transactions.


### B. Decision Threshold Optimization
Threshold selection was performed strictly on the validation set (`y_val`, `cal_val_probs`) by evaluating the Precision-Recall curve.
- **Optimal F1 Threshold Selected**: `0.9771` (tuned strictly on validation fold)
- **Constrained Candidates Evaluated**:
  - Max F1 Candidate: Threshold = `0.9771` (Precision = 1.00000, Recall = 0.99937, F1 = 0.99969)
  - Recall-Constrained Candidate ($\ge 95\%$ Recall): Threshold = `0.9816` (Recall = 0.99811, Precision = 1.00000)
  - FPR-Constrained Candidate ($\le 0.1\%$ FPR): Threshold = `0.0001` (FPR = 0.000996, Recall = 0.99937)

- **Multi-Tier Risk Decision Policy**:
  - `Risk Score < 0.30`: **`APPROVE`** (Low Risk)
  - `0.30 <= Risk Score < 0.9771`: **`MONITOR`** (Medium Risk / Anomaly)
  - `Risk Score >= 0.9771`: **`MANUAL_INVESTIGATION`** (High Risk / Fraud Suspect; `is_fraud_flagged = 1`)

- **Empirical Invariance Proof Across Operating Thresholds**:
  Due to the extreme probability bimodality generated by the tree model on PaySim data (legitimate transactions have $p \le 0.001$, while frauds have $p > 0.977$), there are **zero transactions in the test set between 0.010 and 0.977**. Consequently, setting the operating threshold to any value between `0.02` and `0.97` yields identical test classifications (194,453 True Negatives, 0 False Positives, 2 False Negatives, 2,146 True Positives, F1 = 0.99953). The nominal 0.70 high-tier threshold and the 0.9771 validation-optimized threshold are functionally and operationally equivalent.

## 7. Out-of-Time Test Set Evaluation & Error Analysis

The optimal threshold (`0.9771`) was applied to the **Test Set (Steps 551–743, 196,601 transactions)** (qualified holdout subject to the Section 3 inspection disclosure):

### Test Confusion Matrix:
```
                      Predicted Legitimate (0)    Predicted Fraud (1)
Actual Legitimate (0)          194,453                     0
Actual Fraud (1)                     2                 2,146
```
- **True Negatives**: 194,453
- **False Positives**: **0** (Zero false alarm interruption to legitimate customers)
- **False Negatives**: **2**
- **True Positives**: 2,146

### Error Analysis on False Negatives:
We conducted a deep inspection into the **2 missed fraud transactions** (row indices `6281484` and `6362462` in the source dataset):
1. **Missed Fraud Case #1 (Row Index: 6281484)**:
   - `amount`: 399,045.08
   - `oldbalanceOrg`: 10,399,045.08
   - `is_transfer`: 1
   - `is_full_balance_drain`: 0
   - `dest_prior_tx_count`: 0
   - `predicted_prob`: 0.0001
2. **Missed Fraud Case #2 (Row Index: 6362462)**:
   - `amount`: 7,316,255.05
   - `oldbalanceOrg`: 17,316,255.05
   - `is_transfer`: 1
   - `is_full_balance_drain`: 0
   - `dest_prior_tx_count`: 0
   - `predicted_prob`: 0.0001

#### Root Cause Finding:
In both false negative cases, the originating account was an ultra-high-net-worth account ($> \$10\text{M}$ balance), and the transfer amount was a **partial liquidation** rather than a full account drain (`is_full_balance_drain == 0.0`).

Empirical Analysis of the Account Drain Pattern:
- **PaySim Fraud Population**: Across all 8,213 fraud events, **8,018 (97.63%)** exhibit `is_full_balance_drain == 1.0`. Specifically among TRANSFER frauds, **3,943 out of 4,097 (96.24%)** are full balance drains.
- **PaySim Legitimate Population**: Out of 6,354,407 legitimate transactions, exactly **1 transaction (0.00002%)** exhibits a full balance drain.
- **Tree Model Heuristic**: Because the simulated PaySim data generator created fraud almost exclusively via automated agent balance liquidations, tree algorithms heavily prioritize `is_full_balance_drain`. When a transaction leaves over \$10M remaining in the account, the model lowers its risk estimate to $0.000091$, escaping detection.
- **Generalizability Assessment**: This finding is descriptive evidence of PaySim's underlying agent simulation logic, **not** a generalizable real-world banking rule. In live banking, sophisticated fraudsters intentionally perform partial balance transfers to avoid heuristic balance triggers. This critical synthetic data limitation demonstrates why Phase 05 (Anomaly Detection & Customer Risk Profiling) is essential to complement supervised transaction scoring.
